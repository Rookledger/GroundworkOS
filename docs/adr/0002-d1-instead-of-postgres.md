# 2. Cloudflare D1 (SQLite), replacing Postgres

**Status:** Accepted, implemented

## Context

The database was previously Postgres, accessed through `node-postgres`
(`pg.Pool`) as a module-level singleton living for the whole life of the
Express process (see ADR 0001). Migrations used Drizzle's `push`/
`push-force` scripts against a live connection. CI integration tests ran
against a real Postgres service container. Several queries relied on
Postgres-specific features: `date_trunc('month', ...)`, native boolean
columns, interactive transactions (`db.transaction(async (tx) => ...)`
holding a connection open across awaits), and `greatest()`.

## Decision

Move to Cloudflare D1 (SQLite) with Drizzle ORM. `createDb(d1: D1Database)`
in `lib/db/src/index.ts` builds a request-scoped Drizzle instance — there
is deliberately no module-level connection object, matching the
per-request bindings model described in ADR 0001. Migrations are
versioned SQL files generated by `drizzle-kit generate` and applied with
`wrangler d1 migrations apply` (locally, or `--remote` in production); the
old `push`/`push-force` scripts were dropped since D1 has no live-push
driver. Integration tests now run inside a real Workers runtime
(Miniflare/workerd, via `@cloudflare/vitest-pool-workers`) against a real
local D1 database — see
`artifacts/api-server/vitest.integration.config.ts` — with no external
database or seed container needed in CI.

## Consequences

**Positive**

- Zero-infrastructure local and CI integration testing: no Postgres
  service container to provision, migrate and tear down.
- D1's SQLite engine still supports `INSERT ... ON CONFLICT DO UPDATE ...
RETURNING`, so the atomic sequence-number allocation in
  `artifacts/api-server/src/lib/generateId.ts` (`nextSeqNumber`, used for
  job/quote/invoice numbering) carried over unchanged from the Postgres
  version.

**Negative / tradeoffs**

- No interactive transactions. Multi-statement writes that used to hold a
  Postgres connection open across awaits now have to use `db.batch()` (an
  implicit all-or-nothing D1 transaction), which restricts write patterns
  to statements that don't depend on each other's results within the same
  batch — see the comment in `artifacts/api-server/src/routes/quotes.ts`.
- SQL had to be rewritten for SQLite: `strftime('%Y-%m', ...)` replaces
  `date_trunc('month', ...)`, and boolean comparisons became `s.active =
1` instead of a native boolean column — see
  `artifacts/api-server/src/routes/cis.ts`, which documents both
  translations directly in its query comments (this is also the CIS300
  return query covered by tests added under tech-debt finding #3).
- Local dev state lives under `.wrangler/state` as a local SQLite file;
  `artifacts/api-server/src/seed.ts` was rewritten to only ever open that
  local file (via `better-sqlite3`), so it is structurally unable to
  target `--remote`/production — seeding a real deployment is a deliberate
  dead end, not an oversight.
